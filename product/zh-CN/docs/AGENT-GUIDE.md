# Agent 使用指南

## 1. 从哪里开始

本指南由根 INDEX 的 docs 项进入文档索引，再以 agent-guide 定位。根治理规定身份、工作模式和授权，D:index-spec 规定索引与保护，D:handoff-spec 规定状态、任务、版本与历史，D:design-spec 规定设计指导的提炼、使用和维护。本指南解释怎样操作，不代替这些权威。

先确认用户实际打开位置及固定fieldcase材料根，读取其治理、INDEX、config和HANDOFF。迁入来源可以是非fieldcase工作区，不要求它已具备这些字段；源资料与目标接入分开核对。不要用未填写的root寻找包，也不把父仓、源标记或示例身份当目标事实。

本指南随中文资源包提供。审阅和试用按 §1.1 分流。本文的「随包 README」是固定资源中的 README.md，材料范围和实测边界见该件。章程生效前从指定材料根取用，生效后由 D:upstream 定位实际采用的同语言原件及确切版本或候选批次。实例根 README 是本区入口，取 §5.2.2。原件或所引章节缺失时报告缺口。

从零新建在获准目标展开固定材料；从已有工作区接入按 §7.1 默认建议复制迁入、治理对齐、目标原地新建仓，源区保持。两条路线都须明确治理采用方向；共享接入按 D:index-spec#paths 核对。目标可含本版本材料和同次获准复制产物，不以旧治理存在为由覆盖源区，也不将其自动解释为自治。

### 1.1 现场分流

先判当前职责。用户把候选 README 作为开始入口，给出目标目录和想在其中先做的一件事，便按下表核对现场；无需另说「首用」或「初始化」。明确只做审阅、核对或仅在会话里拟稿的，只做该项，不启动采用问答。用户要试用但暂不写文件时，仍可在会话里引导和拟方案。只在意图确实无法判断时澄清这一点；候选身份、读到示例或目标路径本身都不能代替用户意图和执行授权。

从指定随包 README 确定材料根，另核目标。会话目录、材料根和目标各自确认。目标不存在是正常首用；配置、保护或现行文件异常按根治理报告。

| 核实结果 | Agent 的职责与下一步 |
|---|---|
| 目标不存在、为空，或经核实只有候选材料／未生效模板；没有已准入方案需要接续 | 引导首次采用，按下段发起实际澄清；小目标进入开工方案 |
| 已有准入方案，同次落盘或建设中断 | 读计划、实际文件及交接，按 §7 核对未尽及现有授权，只接续剩余 |
| 章程已生效，具体工作尚未开始 | 待开工；从目标交接取现行事项和已确认范围，核对实际执行授权 |
| 本轮具体工作已开始 | 开发中；从目标交接、现行计划和实物认清成果与剩余，按 §7 或 §8 核实有效授权后续做 |
| 本版实际落版完成 | 保留已落版；有新一轮章程获准生效且具体工作未开始时再转待开工；不重跑首用问答 |
| 发现旧工作区或同次已获准复制内容 | 按 [11] 和 §7.1 分清来源、独立目标和已完成步骤；不覆盖源区或先建空底座仓 |
| 身份、根、配置、来源或文件对不上 | 报告缺口；不凭缺字段、旧 initialized 或父仓识别推定完成、重建或自治 |

选项已可靠确认时，先核本节现场，用同一固定来源核对答案与清单。拟方案取 §2.2 所选预设和 §4，只补适用的未决题。章程拟写与落盘取 §5.1、§5.2、§5.4，涉及 Git 补 §5.3，涉及迁入补 §7.1。选装按所选层和模块从分发配套取相应段落。

受保护正文先过根 §1.3。用现有工具核对清单、B、成员和固定来源时，只回传范围、结果和差异。拟稿、写入和核对时，复用同源、内容未变且已完整读到的段落。工具回传截断时只从原来源补读缺段。触发重读时，按根 §1.4 完成本次全量重读。

首用先核入口和目标，第一条实质回复发起必要澄清。语言未确认时，发 §3.1 的 [1] 前实际读同资源根 AGENTS.md §2.5，按该节及 §2.1 出题。复用可靠答案，只问首个未决必需项；流程说明和小任务稿不替代发问。

发 [1] 后按随包 AGENTS.md §2.5 等待实际答复、重发或走文字回退；回退前与该题有关的正文只提示已发及待答。

按 §4 在会话交完整方案和章程，列小目标、文件及通过条件。用户审定两者并明确授权后，才按 §5.2 建目录、复制或写入。只批文档则待开工；小任务在获准开工后做，已有授权直接沿用。首用不授予根维护身份。

本地材料齐全时可离线准备和建设。核宿主实际读写及所选 Git 能力，基础边界取根治理 §1.5。首次准备留会话，不新增生命周期状态。

## 2. 澄清与快速预设

### 2.1 共同规则

- 第一项必要澄清始终是语言；包语言或系统语言只说明资源／建议，不代用户答复。
- 已确认且可可靠取回的答案复用；已采用完整预设覆盖的项目不重复问。默认预选不算用户已提交。
- 每组允许全部采用默认或展开；采用前用一句话说全该组默认值。新建／迁入路线和治理采用方向分别确认，已有明确选择直接沿用，不由预设、旧定制或保留原件代答。选项呈现按根治理 §2.5。
- 默认澄清工具的发题、呈现、收答及文字回退取根治理 §2.5；测试载体按 §2.3 的选择与核验办理。模块确有必要参数才按模块说明补问，不预造参数。
- 澄清期间不边问边创建目录。最终完整方案准入且用户明确执行后，才保存采用原件、复制获准内容并实施；治理对齐完成后才进入本次目标建仓。
- 根维护者由用户明确指定，身份取根治理 §1.1。按 §3.6 核对承担者并拟定本次引导会话标题。

### 2.2 三种引导节奏

| 方式 | 用法 |
|---|---|
| 逐组引导，默认 | 按下列组依次确认；每组可采用已完整说明的默认或展开 |
| 标准快速 | 整组展示并确认标准预设；补缺失的语言、接入路线、治理方向、名称／身份、署名、冲突与授权 |
| 全模块快速 | 整组展示同版兼容完整预设及实际模块名单；缺材料或未知依赖不能静默略过 |

标准预设完整说明：专业采用本区D及K／R／M／T，先确认接入方式，项目区建议取 §3.2，其余本地区目录默认为 docs、knowledge、references、materials、temp；本地 Git，实际仓根与跟踪范围按方案确认，D 随本区维护。分支研发、标准讲解、表格点验、共享开发；D三核心与规范目录常态保护，资料保护按实际治理／规范生成，强制检查开启、恢复提醒ask，不额外加对象。仅核心及所选层必要规则，不额外启用三个模块或项目内Skills。语言、根身份、实际名称／路径核实和缺失署名仍须确认。

上述本地层路径是独立新建的默认，不是治理方向或迁移方式的默认答复。复用上级共享层时须逐层说明真实入口、权限、协议及仓库差异；迁入仍按复制、对齐、目标建仓排序。不得强套与现场不兼容的预设。

全模块预设在上述选择上采用该固定发布包明确提供且兼容的知识获取、跨区协作、无人值守及对应可用项目内封装；必须逐项展示实际名单、依赖与配套，不把未提供的 Skills 或尚未下载的材料称作已备齐。三个业务模块的兼容来源仍各自核对。

这两种预设只减少问答，不降低来源检查、完整方案、执行授权或收尾核验。若用户不采用预设，转逐组引导；无 Git／直接 main 等选择与预设冲突时，回对应组明确处理，不拼出不可执行方案。

随包 README §1.1 的极简无 Git 路线按逐组确认 [4] 极简、[7] 暂不启用、[9] 仅核心及所选层必要规则。沿用可靠答复，跳过未选层和 Git 专属题。§4 核语言、维护者、来源、实际根、目标号、文件及授权。

### 2.3 可选作答载体

载体是在哪里作答，引导节奏是逐组确认还是整组采用预设，二者分别选择。默认载体及其文字回退取根治理 §2.5；先完成原 [1] 语言首问，再可自愿选择测试载体，跳过选择即沿用默认。各载体沿用同一套现行题号、选项及其含义。原 30 个编号保留，[7.1] 供旧答卷回查。旧答卷先核来源版本／候选批次与用户实际意图，不把旧“极简K＋T”自动解释为本版取消K；差异在完整方案集中确认，不增题号或擅自清除既有选择。

| 载体 | 采用条件与结果交回 |
|---|---|
| 澄清工具／文字，默认 | 按根治理 §2.5 处理呈现、重发及文字回退，沿用现有题文与预设，核对实际答复 |
| Codex Visualize，测试 | 核实本会话实际能力后，由用户提交，并在宿主要求时完成确认；完整答案实际进入当前会话后校验 |
| 其他 Harness 的 HTML，测试 | 先核实可展示界面；按实际能力消息回传，或复制结果／保存 JSON 后交回 Agent；不预设所有宿主都有桥接接口 |

复制和保存 JSON 从同一份答案生成，使用同一套题目标识及答案含义；[3.1]／[3.2] 在 JSON 中使用字符串键，[4] 选项 3 的 K／R／M 选择明细须随同题交回；[9.1]–[9.4] 仍按各自题号回收。[5] 采用所列目录或 [5.1] 采用推荐路径时，随原题答案保留项目区的实际路径。旧答卷按其固定来源及当时题面解释路径选择，无法核实时只补问缺失的路径。旧载体缺少必要选择时补问，不猜填。默认值仍须用户实际提交，不能把预选或组件状态保存当答复。下载文件不表示 Agent 已收到，不把仅在界面显示成功当作回传成功。

收到消息或用户明确指定的结果文件后，核对题目标识、选项范围、必需的自由填写值和与本轮提交的对应关系；内容缺失、无效 JSON、未知题目或冲突先集中澄清，不猜补、不写入 config。重复收到相同结果不重复实施；前后不同则按用户实际明确的最新提交核对。

答案接收、完整方案确认及执行授权分别办理；单独提交普通答案不触发初始化。原 [12] 只有完整方案已展示、用户明确提交其执行选项且授权意思清楚、仍在原流程内时，才按既有规则处理；界面预置、测试样例或程序自行添加的 authorized=true 等字段不能代替该答复。

选择测试载体不自行授予创建界面文件、启动服务或外部发送权限。当前只提供候选规则与最小验证方案；实际验证通过前不标正式可用，缺少能力时可继续默认路径。实验受阻时保留已同意的候选方向，说明影响并集中交用户决定保留或延后，不自行删除。

## 3. 初始化完整题文

### 3.1 语言、方式与工作区

```text
[1] 使用哪种语言初始化并长期使用？
1. 中文（zh-CN）
2. English（en-US）
说明：按可用环境信号推荐，但由用户确认；初始化后不提供日常语言切换。
```

```text
[2] Agent 采用哪种初始化交互方式？
1. 逐组引导（默认）：每组可全用默认或展开
2. 标准快速：整组确认标准预设，由 Agent 落地
3. 全模块快速：整组确认同版完整预设及兼容模块，由 Agent 落地
说明：三者均由 Agent 交互并按授权执行；快速只减少重复问答，保留相同的授权与核验要求。
```

```text
[3] 工作区叫什么？
1. 使用当前目录名（默认建议）
2. 自行填写名称
说明：同时展示检测到的根绝对路径；工作区名称不必等于文件夹名。
```

```text
[3.1] 本次怎样接入工作区？
1. 从零新建
2. 从已有工作区复制迁入
说明：先核对来源与独立目标。迁入默认建议复制、治理对齐，再在目标原地建仓，源区保持；用户明确强制移动时另列源处置及恢复范围，不默认移动。
```

```text
[3.2] 采用哪一种治理方向？
1. 完全按 fieldcase 管理
2. 保留私有采用原件，区内部分或全部治理自治
说明：不默认替用户选择；已明确则复用。原件留存不等于自治，方向1保留完整管理要求，方向2明确采用范围、实现及维护责任。
```

选定语言资源不存在时，不只改 locale；用问题 10 核对该语言完整配套。工作区名与根位置由 HANDOFF 单点记录，根维护身份另核用户指定。

### 3.2 层与目录

首次发出 [4] 组合题，或用户返回该题改选时，按根治理 §2.5，先在同一轮会话正文写清以下层的全称、用途和三种组合的影响，再给原题和选项。文字作答也先说明，再给等效菜单。正文要让第一次看到这道题的人能够据此选择，意思齐备后可收短表述。

| 层 | 用途 |
|---|---|
| D（Docs，文档层） | 存放本区工作文档和现行规范，随根维护，不另设 D 仓或层号。 |
| T（Temp，临时层） | 存放缓存、待归位资料、施工中间产物、审计证据和备份等，按实际 T 总索引取用。 |
| K（Knowledge，知识库层） | 积累和检索可复用的知识，按需自建、复用共享库或按批准清单导入。 |
| R（References，参考与证据层） | 存放供查阅的参考资料、快照和核验证据。 |
| M（Materials，生产材料层） | 存放和维护制作任务用的文稿、模板、素材等。 |

根入口、D 和 T 是三种组合的基础。专业同时采用 K、R、M。极简只采用基础组合。自选逐层决定是否采用 K、R、M。采用某层表示把相应入口纳入方案，实际来源和目录随后确认。启用资料层不自动创建 Agent。

```text
[4] 使用哪些文档／资料组合？
1. 专业（默认）：采用本区 D 及 K／R／M／T，三类资料都有入口。
2. 极简：仅用根入口＋D＋T，暂不采用 K／R／M。
3. 自选：保留 D／T，逐层点选是否采用 K／R／M。
```

选 [4] 的 3 后，按根治理 §2.5 先说明各可用资料层的作用。使用每题只支持单选的澄清工具时，把下表中可用的各层放在同一组，每层一道「采用／不采用」单选题，答完一起提交。

| 题干及采用影响 | 采用 | 不采用 |
|---|---|---|
| [4] 是否采用 K 知识库？采用后增加可检索知识的入口，可自建、复用实际共享库或按批准清单导入。 | 采用 K | 不采用 K |
| [4] 是否采用 R 参考与证据？采用后增加参考资料和证据的入口，按登记范围取用。 | 采用 R | 不采用 R |
| [4] 是否采用 M 生产材料？采用后增加生产材料的存放、维护和取用入口。 | 采用 M | 不采用 M |

发单选题前检查工具请求：每行的两个答案须分别出现在点选项字段（Codex 为 `options`）。点选项缺失就先补齐，不能改让用户填写层名。澄清题未显示时的重发与文字回退按根治理 §2.5；明确选测试载体时按 §2.3。

收齐后，把选择记为 [4] 选项 3 的明细，不另编题号。未选层不在本次接入，也不因此移除既有内容。本组给出的各层均提交「不采用」才记全不选；缺答只补问缺的项。

确认接入方式后，先分别核对要承载的项目和这些项目的治理边界，再给出 [5] 或快速预设的目录建议。已有明确的目录或子区安排时沿用。迁入先核既有入口与实际依赖，将需要调整的路径和归属列入方案。只有相关信息不明确且会影响布局或维护时才补问。

| 已确认的场景 | 项目区建议 |
|---|---|
| 单项目，由本区维护 | 推荐 `project/`，业务文件直接放入该目录。规则、交接和维护职责归本区。 |
| 多项目，由本区统一维护 | 推荐 `projects/`，各项目各有目录，共用本区治理和交接。 |
| 项目确需独立维护、授权或交接 | 在项目区内按实际需要设子工作区。按适用治理确认其维护者、职责和交接边界。 |

## 5. 首次章程准备与建设

### 5.1 留存采用原件

D:upstream指向实际采用或升级比较所需的fieldcase版本原件，默认docs/upstream/fieldcase/<精确版本或候选批次>/；实际入口、语言和保存范围在D总INDEX说明。Agent从固定来源取得所需文件，保持包内相对结构，不将用户定制反写为官方原件，不为此复制整个上游仓历史。

在修改采用工作文件前留存未修改原件；核心、所选模块及其比较所需INDEX／ADOPTION配套按实际范围保存。源码包、正式用户包和未发布候选分别核身份，不从floating main或latest拼装。未发布候选须明确试用准入、固定整组清单和唯一批次；同号不同内容不覆盖旧原件，也不伪造发布标签。

整包批次和语言取同一固定资源根的随包 README §1，与随附固定清单核对。只有解包实物时，用其中的随包 README 和实际成员清单固定本次采用对象，随原件保存。配套材料来源查分发索引，只用于定位材料；不得用它、目录名或同版本号推定整包批次。旧包未标整包批次时，按可唯一定位的原固定清单或正式发布记录确认。来源冲突或仍不能唯一确认时，报告缺口，暂停依赖该来源的采用或升级。

已有采用记录时，从 config 核心及模块来源版本回查 D:upstream 的实际原件入口，分别确认所用固定批次、语言及范围。例如候选 A 和 B 都写 0.1.0.0，当前采用入口指 A 时，取得 B 只增加比较材料。完成对 B 的采用与核验后，才按 §12.2 切换入口。

旧实例尚无现行指向时，先用原采用记录与固定清单核唯一对应的原件，纳入已批准的索引修订。缺原件时只重取已选的同一固定版本或候选批次。无法唯一确定、取回或验证时，报告比较依据缺口，待核实后再继续依赖该原件的升级。

原件是比较依据，按原样保护，不作为当前生效规范或日常全量重读对象。Git记录或用户快照则承担本批改前现场恢复；两类依据不互代，清理按各自授权。D:upstream未形成时不预建空原件目录或虚构可用入口。

### 5.2 章程落盘与本轮开工

先在会话收敛完整方案和章程稿；不另建初始化阶段文档。用户准入后，按文档授权集中落盘，首次生效为待开工。文档准备所需目录、原件、治理、配置及索引随方案办理，不代表环境、业务迁入或仓库已建设完成。旧源管理文件作为来源保留，不覆盖目标已准入章程。

按 §3.6 处理当前引导会话标题。有明确授权且宿主支持时，在初始化实施期间设置标题并核实实际结果。标题变更可与完整方案一次授权，已同名直接核对。无法设置或核实时，报告实际标题及缺口，继续已获准的其余步骤。仅对当前引导会话设置标题。在现有交接身份记录中填用户指定的维护者，有可用会话定位时一并登记。

1. 依§5.1保存采用原件，填写实际身份、root、本轮目标version、已准入需求及必要依据。纯章程准备首次落盘为待开工；同次具体工程已开始则记开发中，补写文档不回退状态。无真实分支时不预填dev或标签，不写initialized。 填写交接时，把根 AGENTS §4.2 的 Git 和分支两行一并从占位换成已准入选择。未建仓时只记后续选择，不写实际分支或提交；不选 Git 时分支不适用。
2. 不论K是否采用或复用外部库，本区三核心规范均装入D专用spec目录，默认docs/spec。D位置由根docs入口维护，不增加配置路径或独立D版本／仓。
3. D总INDEX登记index-spec、handoff-spec、design-spec的规范类型、真实入口及B；直接以D:标识引用，不新增根rule-*别名。提供侧同名规范沿原权威与范围生效，不替换本区完整模型。
4. D／T就位后按选择登记K／R／M；K可自建、共享或按清单导入，未选不预建。落实实际协议、维护权、locale、采用方向、资料保护与消费选择。D核心保护不依资料数组；共享层不复制根、代建仓或改总索引，不另建第二T。
5. 所选模块规则可随本次章程和配套落盘，将其条款及规范纳入同次核验。获取、通信和自动任务仍按各自授权启动。
6. 核对适用上位治理、三态及首次建仓的适用关系；按其要求补shared_layer／root_governance，缺值或权限不猜补，不自行豁免。新层在没有可靠固定基线时使用development、stable_ref=null，后续按实际准入及定位维护。
7. 按根 §1.3 核 D 规范条目、实际 B 和完整目录成员，再按根 §1.4 全量重读已生效治理及规范。查条文或写本次重读回执时，直接用本次已完整读到的原文。资料另核同源固定来源。核心及模块实际采用的配套核验通过后，按根治理 §6 同步来源版本与 D:upstream 入口，并回读核对实际版本及入口。文档写入未齐时报告具体缺口，状态不能代替实际核验。
8. 只批文档则在待开工停步；同次授权含工程时，实际开工前转开发中并接续。环境、依赖、业务复制、建仓及提交均是具体工作。迁入工程按复制→治理／入口核对→目标原地建仓排序，不先建空仓再导入业务；从零建设按已准入任务依赖执行。

同次施工只续仍获授权的剩余事项，具体进度记既有交接；用户暂停或转讨论后，施工恢复须明确执行。集中写入和跨仓提交不构成原子事务，不虚报未完成步骤。

### 5.3 所选 Git 操作

Git建仓、首提交和建立本轮分支均须列入具体任务及执行授权；开始时为开发中，使用章程已确认的同一目标号。迁入先完成获准业务复制与治理／入口核对，再目标原地建仓；源.git、父仓及外部共享仓不作目标仓。核实真实根与署名，按清单暂存，不全量收录未知内容。

| 范围 | 首提交边界 |
|---|---|
| 获准本区仓库 | 按真实仓根逐路径核对已准入的治理、交接、说明及许可、配置、索引、规范、忽略、采用原件和其他受控内容。已选资料层依其跟踪范围处理，空层仍有可达入口 |
| T | 无独立仓。T 产物排除，只跟踪本区拥有的 T 总 INDEX。worktree 仍属其原仓 |
| 复用外部 K／R／M | 沿实际仓库与维护权。本区仅跟踪获准的本区文件与引用入口 |

默认 T 位置的忽略示意：

```gitignore
/temp/*
!/temp/INDEX.md
```

按实际受控清单、目录位置和仓库边界派生忽略。排除外部共享目录、其余仓库与 T 产物，保留应受控治理件。只核对必要路径，包括自定义或深层 T 及应跟踪的总 INDEX。

本次准入且确无历史提交的新仓，按D:handoff-spec#branch在main提交已准入章程及必要文件作为共同起点；首版建议0.1.0.0，起点与本轮dev使用同号。分支研发在实施后续任务前建dev/<本轮版本>，其后main只按正式收口前进；直接main／自定沿已准入规则。已有提交不重做起点，固定标签不移动；存在未清除上位冲突或必要授权缺口时停止受影响Git链，不重复索取已有明确授权。

各仓按实际授权办理，T 不另建仓，外部共享仓保持。README、许可和采用原件等应受控内容按真实清单纳入；未启用资源只作T缓存。首提交不自动表示接入已验收、正式落版或可供正式消费。

无需账号、远程仓或联网。命令失败时记录所在仓、已完成提交和剩余动作，不从头重建，不用 --amend、重置或强推掩盖已供消费的历史。

### 5.4 固定定位与本轮收尾

按 §4 清单核对文档、选择、来源、语言、入口、B、成员、复制及适配、实际仓根／分支和所选提交。进度与未尽记现行交接，无 initialized 或初始化标签；讨论或自检不回退「开发中」，状态以实际内容佐证。

不能在一个提交里写它自身尚未生成的提交ID。若实际消费需要固定标签或副本定位，先列入方案，形成完整对象后按授权创建并核对；未创建或未核实不记为已有，固定标签不移动。

资料表只记实际采用的来源，接续从原固定源继续。无可靠定位用 stable_ref=null，起点提交不自动成基线。按 D:index-spec#source 分别核本区及源无 Git 的边界与外部实际保障。

报告源／目标、版本及状态、文件、实际仓库、结果与未尽，以及证据及点验入口。落版和发布按根治理分别放行；证据和状态按实际。已有权限的后续工作接续，其余返回讨论。

| 情况 | 操作 |

### 7.1 从已有工作区复制迁入

默认建议顺序是复制迁入、治理对齐、目标原地建仓。它适用于两种治理采用方向；用户明确强制要求移动时，须单列源目录处置、权限、恢复与验证，不把移动当默认或以复制名义删除源区。

```text
类型：流程｜复制迁入
┌ 固定来源、复制获准内容，源区保持
│ → 按采用方向对齐治理及实际入口
│ → 目标原地建仓（若选Git）并核验
└ → 接续试用与验收；会话切换另按授权
```

1. 核对用户指定职责、来源及独立目标。先确认接入路线与治理方向，沿用已明确选择；盘点源实际文件、未提交／未跟踪／删除状态、必要历史和依赖。Git HEAD不能替代未提交业务。
2. 展示完整复制清单、批次和目标，区分原样保留与路径适配；来源及治理原件、业务资料和本次恢复依据分别定位。源区保持。源目录与目标结构不对应时，按内容用途、维护归属和实际依赖列出原位置、拟落点及需更新的引用。遇到归属不明、冲突或未预见的条目，先列待裁、保留原件，确认后再处理该项。目标已有不明内容或仓库时先消歧，不覆盖。
3. 获执行授权后先留存固定fieldcase原件与本次源依据，再复制获准内容；可按功能依赖分批。不得静默遗漏附件、裁决、未尽或历史，也不复制源.git覆盖目标；需历史时按授权保留原仓或只读历史副本。
4. 核对原样内容与源依据一致，记录排除、源变化及剩余依赖。恢复／原结构副本保持只读用途，写出型脚本只在另获准工作副本运行；源变动或目标后续修改不强制覆盖。
5. 复制到位后按 governance_adoption 对齐目标治理。方向1以已准入fieldcase完整模板和统一接入规则生成生效文件，旧管理办法只作迁移依据；方向2落实已准入自治实现、采用范围和维护责任。原业务规则、事实、用户裁决及必要历史按新治理的职责落点保留，不能因治理替换抹掉，也不把业务规范当作通用管理方式的替代。
6. 更新目标当前入口、config与HANDOFF，核对共享层、真实规范引用、保护及完成条件；不沿用源root、状态或源仓识别结果冒称目标完成，源initialized不参与目标判断。复制与适配分别核验，源历史不批量改写。
7. 完成复制和治理对齐后，按 §5.3 在目标原地新建自己的仓库；源区和共享层仓不动，源业务版本与目标本轮版本分别保留。用户明确选择无Git时不建仓，记录实际能力边界。
8. 按§5.4核对本次清单、三态、真实仓根及所选提交后收尾；复制、治理对齐、建仓、自检和用户验收分别记录，具体工程完成不自动退回待开工。同次中断按清单只续剩余，不重复建仓或覆盖已完成成果。
9. 若另有会话目录切换，先交迁入产物和快审材料；按约定确认并获切换授权后，核对项目关联会话及影响范围，只变更获准对象；再核原会话、项目归属、主次目录及实际cwd，并验证接续。文件已迁入不证明会话已切换，不擅自新建会话替代原会话迁移。

## 8. 正常接手与一个小任务

1. 按根治理全量重读已对本工作区生效的治理与规范，核对实际工作区、版本、分支、状态及原资料依赖；子工作区使用本区交接。不能把读取治理当作获准实施。 本区模型从D实际条目读取当前准入文件；资料pin不换读管理规则，其它已适用上位规范仍按实际来源全读。
2. 依生效章程、事项和现场接续，核对待开工／开发中／已落版；只补本次未明确的目标、范围和完成判据，不因缺initialized或待开工重跑问卷。
3. 将本次目标、来源、边界、所需资料和验收放到当前 E，按授权登记；无写入授权时先会话拟稿。
4. 用户明确执行后，在约定范围完成一个小型文档任务，例如整理一份用户指定说明并核对引用；不要自行发明业务任务或内容。
5. 按实际需要固定 K 等来源，接续恢复同一来源；业务文档事实、规范依据和候选意见分清。
6. 验证实际文档、入口和约定效果，给用户可点验路径、操作与通过条件；记录结果、缺口及未提交／未发布状态，回到讨论或按已授权任务继续。

普通执行默认直接施工；用户要求预检时按根治理集中申领必要权限并遵守交互次数及收口规则。是否预检不减免必要验证与验收。换版时按 D:handoff-spec#size 报告交接体量，告警不替代完整记录或用户准入。

实际工作沿章程已确认的本轮号及分支规则推进，首版建设不额外消耗一个初始化版本。新增版本按实际范围及准入确定；按实际仓库与授权边界办理。无 Git 仍可完整做文档任务，历史保障如实说明。

### 8.1 设计事务的首次建立与接续

先按 D:design-spec#scope、D:design-spec#use 识别设计对象、场景和适用约束。普通文档任务没有设计事务时照常推进，不生成空 DESIGN；读取规范不等于获得创建或施工权限。

已有品牌、项目或领域设计规范时，先按本区已准入治理或所属 INDEX 的实际入口接入，保留原适用范围、参数及资产权威。确无合适载体且任务需要时，先拟本区根内具体路径、自足正文、适用范围及登记方案，经原有准入和执行流程建立；不新增初始化必答题、配置开关或设计选装模块。

后续设计任务读取内容边界及适用指导，再取关联资产或实现入口。主动从获准范围的既有规则、成功做法、已核实问题及修正中提炼，区分事实和裁定，不把一次成败推广为全区通则；必要历史定向读取，不漫读全部历史或源码。

设计指导、参数、问题和任务事实按 D:design-spec#split 分流；出现新判据、反证、边界或前提变化时先拟修订，核对用户原始裁定及补充、排除项，准入后更新必要文件和有效引用。文档核验、作品或实现复验、用户验收分别记录，未测不记通过。

跨区可复用内容先向用户提建议；是否共享及其实际入口由用户决定。没有采用跨区模块也能独立完成本区 DESIGN 的建立与维护，不能为上升建议自动安装模块或发送消息。

## 9. 消费、保护与配置异常操作

### 9.1 固定资料来源

从 config 读默认策略，在当前 HANDOFF 一处资料依赖表记录实际层、采用方式、内容版本与固定定位。开发用确定提交，正式用已核实固定基线；同一次任务的 INDEX、成员和正文必须来自同一来源。

新任务／明确采用更新时才切换基准；换会话、压缩或中断接续不跟新。按资料实际所属的仓库或固定副本读取同源 INDEX、成员和正文，分别核对内容版本。不必切换维护者工作目录；人工需要实际目录时再展开到 T。

比较候选不改 pin；实际试用在同处补试用范围和原正式依赖。指定 K 不连带换 R／M 或根治理，不替换全局正式入口，不自动追随 dev；结束试用恢复原依赖或采用获准新基线。

正式消费采用同仓 T worktree 研发，保留共同历史；根／层按所选分支方式收口。无 Git 或直接 main 的限制在方案中如实处理，不伪造快照或隔离能力。

### 9.2 保护检查与偏差报告

先按根治理启动检查：实例规范先核根docs入口、D实际条目及专用规范目录；资料另按其固定源核file、pattern及directory范围。#./只为directory确定具名文件的父目录，不能当章键或猜路径。完整成员与逐文件B均核对，不跨来源／用途去重，不算目录总大小、不做哈希。

偏差报告样式：

```text
错误码：INDEX_BYTES_MISMATCH
层／标识：K:<实际标识>
固定来源：<本次确定的提交或本地现状>
实际入口：<由所属索引解析的目标>
登记值／实际值：<B>／<B>
影响：<因此停止的任务>
建议：由有权限维护者核明正文或索引差异，按授权修复后明确采用修复来源并复验。
```

消费方不把大小改成当前值来消错，不用旧 INDEX 检查新文件。B 相同不证明正文未变；正文已按权限修改且登记没变时，不为了“有索引 diff”加无意义字段。

### 9.3 配置异常与排障

按根治理的完整字段／异常表逐项核对：语法与重复键、精确来源、已初始化语言、保护／消费类型和取值、实际保护范围、模块来源、展示偏好和未知字段。

关键项不猜补；展示偏好可以当轮说明后临时 standard／table；未知字段先找本地已准入定义，无法解释则保留并报告，不赋义、不写回。

例如 enforce 为字符串 false，应报告类型不符并停止依赖它的执行；拼错 enfoce 不能修成用户想关闭保护。locale 改成另一个值不代表文档和历史已完成翻译。

仅根在用户明确排障授权内可解除既定索引偏差强制阻断；轻量检查和实际缺口仍在。restore_prompt=never-ask 只抑制恢复提醒，修复后不自行开回保护，也不反复追问；用户主动要求恢复时再按授权修改。

## 10. 模块发现与按需采用

### 10.1 本地先查，再按需联网

业务出现缺口时先核对已装能力，再查随包 README 和实际分发资源索引。找不到所需兼容材料，先说明官方来源、需要取得的内容与配套，询问用户是否联网。

获取精确固定包及必要说明；用户可仅装兼容模块、评估整体升级或保持现状。不因为上游有新版阻断当前任务，不默认后台轮询，不静默取 latest 或浮动 main 的零散文件。

独立布局的已备材料从根T入口的distribution定位fieldcase/INDEX.md；复用上级T且无该分类时，由docs INDEX登记固定包内分发材料的真实入口，优先复用已留原件，不造公共分类或第二套T。先核对其来源与文件清单，再读 adoption 配套说明。该说明承载 R／M 和三个模块的实际目标、完整必要差异、组合与核验，不代替现行治理，也不表示已经安装。

### 10.2 集成步骤

1. 从资源索引核实模块标识、精确版本、适用核心基线、前置层／模块、配套文件／条款和必要参数。
2. 核对实际已装状态；config 条目、文件存在与行为配套一致才算采用。只有下载或一份 Skill 不算安装。
3. 将拟变更、目录、原件保存、配置、索引与必要核验交用户审定并明确执行；治理配套全文先展示。
4. 保存所选模块原件，方法规范统一装入本区D/spec，由D总INDEX登记真实入口及B，不新增根别名。知识获取方法可先安装，原始件任务可用T，正式产出须先明确K目标。共享K治理不代改，共享T仅复用合法契约入口；缺实际所需依赖时报明，不造第二T或覆盖上级索引。继承与本区安装分记，新模式显式登记，配套核验完成才写来源。
5. 核验行为、保护登记和必要入口。成功后按 §12.2 同步记录该模块的 modules.<标识>.source_version 和 D:upstream 原件入口，核心来源保持原采用记录。
6. 在交接记实际结果与未尽，说明已经采用的内容和以后发现入口，回到讨论；不继续逐个催装未选模块。

按配套说明合并同一文件的改动，现行索引只登记已选内容。跨区模块另须落实契约专用索引及其通用索引模型例外；无人值守只接入获准模式，不启动任务。现有初始化问卷和预设沿用，不因材料增加自动改变用户选择；本包没有另行提供项目内 Skill 封装。

模块可以为无人值守任务提供预检选择、线程 heartbeat、连续迭代及可另行启用的熔断复活；实际能力以固定兼容材料及已并入根 AGENTS 的定义为准。安装只使规则就位，不启动任务；用户明确任务及对应执行方式后才按规则办理。宿主不支持的 Goal、heartbeat 或通信能力须报告缺口及影响，不能记为完整自动化已通过。

模块也可只是一组现有文件修改；不用为了形式新建 spec。Skills 的实际封装、参数和目录按兼容说明及用户选择，不预定数量，不全局强装。

卸载同样审查实际规则、入口、依赖和定制范围；删除 config 条目不等于卸载完成。单装模块不改变 fieldcase_version，核心升级不批量替所有模块更新来源。

## 11. 官方更新与用户定制比较

先从config核治理采用方向；方向1核全部适用管理要求，方向2核已准入的采用范围与自治实现。旧实例缺少方向时先核明，不凭定制痕迹推断，也不在升级中自动切换。 同时检查D现行规范及其真实条目；提供侧同名文件或层版本更新不等于本区规则升级，纯位置迁移不直接改来源号。

### 11.1 三份材料

按 §5.1 从 D:upstream 找到现行核心及相关模块的确切采用原件。从当前 INDEX 解析用户现行文件，按授权准备新固定原件。比较的三份材料分别核实，旧原件无法找回时按 §5.1 报告缺口。

| 比较 | 认识 |
|---|---|
| 旧官方 ↔ 当前实例 | 用户本地定制 |
| 旧官方 ↔ 新官方 | 上游增改删 |
| 合看两组差异 | 哪些保留、采用、合并或暂缓 |

先按稳定标识对应对象；名称、实际根、内部路径、语言、仓库和偏好按既有选择保留，不把它们逐项误报成治理冲突。HANDOFF的事项、现场与历史保留必要认识。

升级三态时，按本次准入的当前工作集、已开始任务及实际落版证据判断，不从旧状态词或initialized直接换算。旧初始化基线、固定标签、证据和历史按原来源保留，不追认落版、不重跑已完成工程、不重置已有本地版号。旧未初始化／初始化中／待开工无法唯一映射时，列方案请用户确认；只在获准的现行文档清单移除fieldcase旧标记，自治自定义字段按其权威办理。

### 11.2 逐项裁定

| 情况 | 建议处理 |
|---|---|
| 仅官方修改 | 解释影响并提议采用，仍核适用性 |
| 仅本地定制 | 业务与开放配置保留；方向1的管理偏离须解释并按fieldcase要求对齐或待裁定，方向2按其准入实现评估保留 |
| 双方改同一约定 | 展示位置、双方意图、冲突、建议结果和影响，交用户裁定 |
| 新依赖或必填字段 | 将必要配套列入同一方案，不单独启用入口文件 |
| 官方删除而本地仍用 | 解释受影响引用和行为，决定保留或迁移 |

不设计自动权重打分代替用户。复杂治理合并按根治理 §2.2 在讨论收口、用户启动下一轮前给出推理建议；下一轮为治理拟稿时同步提醒至少 xhigh，并先核对档位可用性。用户直接发令按当前设置与原模式办理，后续调档建议面向下一轮；实际生效范围取宿主确认信息，不擅自改模型或借高档位扩大范围。

## 12. 同型备份、应用与定向恢复

### 12.1 修改之前核实恢复依据

按根治理 §6 核实可用的改前依据。清单逐路径标记增、改、删、迁移、改前是否存在及对应来源。范围包括实际改动的治理、配置、索引、规范、指南、忽略和用户自加规则，以及来源字段和 D:upstream 当前定位的原值。确需触及业务、知识正文或历史时先纳入批准范围。清单和恢复定位使用已有方案或 HANDOFF。

| 现场 | 必要处理 |
|---|---|
| 已有Git记录完整覆盖本批改前状态 | 核真实仓根、受控路径、固定提交及实际改前内容，记录清单和恢复定位；不强制复制文件快照或创建D:backups |
| 无Git，或提交未覆盖实际未提交／未跟踪／忽略文件等必要内容 | 对未覆盖的本批文件保存必要同型快照；可与已足够的Git记录组合，不拷整个工作区 |
| 只有移动分支名、父仓识别或未核实的“有Git” | 不算可靠恢复点，先查清实际路径、内容和固定定位 |
| 恢复依据缺失、不可达或无法覆盖本批状态 | 停在修改受影响文件之前，报告缺口并继续独立获准事项 |

逐路径核对真实所属仓及恢复来源，分别记录覆盖该路径的固定提交或快照。已有提交只证明其实际内容；未提交变化须被本次依据真实覆盖。需要新提交、标签、stash或其他保存动作时，必须已在明确授权内，不擅自纳入用户无关改动，也不为凑恢复点清空或重置工作树。

只有确需物理文件快照时，采用D:backups的实际入口，默认docs/backups/<日期>/<升级批次>/。批次INDEX放snapshot外，记本次范围、每项恢复来源、增改删／迁移和恢复步骤；snapshot按用户真实相对目录存文件，不把已有备份、采用原件、.git或无关资料递归复制进去。同日重试不覆盖旧批次；不因Git后来可用删除旧快照。

Git已足够且本次未产生文件快照时，D索引不登记虚构backups入口，也不为存一个提交号建立空备份目录。此处简化只针对治理资源升级的操作恢复，常规落版及备份仍沿D:handoff-spec和适用上位要求。

### 12.2 应用与来源收尾

原件及本批恢复依据核实后，按用户准入的三方比较结果应用；采用方向、角色、名称、真实root、业务事实、已有版本和有效定制不被新模板覆盖。同步D位置／引用、实际资料入口、保护、成员、B和派生配置，保持单一写入持有者。移动只处理获准现行工作文件，不迁动原件、旧证据或他区内容。

现行文件、必要配套、恢复依据和约定核验齐备后，按根治理 §6 同步本次实际采用的 config 来源版本、根 INDEX 核心版本展示及 D:upstream 确切原件入口。回读三处和实际原件，核对应对象、版本、批次、语言和范围。候选同号时，版本值可以保持，仍核对定位到已采用的那一批。

只处理本次实际采用的核心或模块，其他原件与来源保留。若应用或来源更新中断，在既有 HANDOFF 或任务记录报告已完成、未尽和原依据，按 §7 与 §12.3 补齐或恢复。获准提交、实例版本、来源采用、用户验收、落版和公开发布按各自证据核实。

### 12.3 失败与定向恢复

| 失败位置 | 处理 |
|---|---|
| 获取／比较依据不足 | 保留当前实例，说明缺原件或可靠来源，不猜合并 |
| 恢复依据核对未过 | 不改受影响现行文件，不把“有Git”代作覆盖证明 |
| 部分应用或核验失败 | 在原授权内修复；不能完成时按已准入清单和每项恢复来源处理 |
| 已有升级提交需撤回 | 按范围恢复并形成获准恢复提交，保留已供消费历史，不擅重置或强推 |
| 升级后另有独立修改 | 先区分范围，交用户处理冲突，不用恢复丢弃后续成果 |

修改／删除项从已核实Git来源或文件快照取回；新增项先确认无后续修改及使用才移除；迁移按记录恢复位置并同步索引、配置和来源。不能以整仓reset或整包覆盖代替路径清单；用户未授权恢复提交时不自行提交，按实际结果报告剩余。

恢复后核真实入口、保护、B及必要内容。涉及来源收尾的，按清单复核 config、根 INDEX 核心版本展示和 D:upstream 的改前入口。保留本次处理结论、证据和仍需授权事项。无Git不声称产生恢复提交；快照或Git也不保证恢复本批未覆盖的业务内容。旧采用原件、固定标签、历史及原始报告保持其原来源，结构升级不倒改既成证据。

## 13. 人工点验与交付
