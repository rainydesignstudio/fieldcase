# 交接、版本与接续规范

## 1. 目的与分工 <a name="goal"></a>

交接须让不了解原会话的接手者回答：实际工作区在哪，当前状态和任务是什么，已经裁定什么，哪些还需授权，下一步怎样验证，以及必要历史从哪里取回。

- 根治理保留身份、授权和长期判断边界；HANDOFF 承载实例现场、当前事项、当前需求及事实接续；INDEX 管实际入口，config 管已确认选择和官方来源。
- 一个现行HANDOFF只承载一个当前版本工作集。已准入章程可在待开工时记录目标版本；材料占位不冒充生效版本。未实施需求也须登记，不以写入交接取得执行权限。
- 初始化、普通研发、候选待审、用户验收、正式落版和公开发布分别记录，不能用其中一个状态推定其余通过。
- 资料依赖以本规范 #pin 的当前记录恢复；索引、保护和固定来源读取取 D:index-spec。模块只有在实际采用并核对配套后才产生适用规则。
- 例子中的版本、路径和提交均为格式示意，不是已经存在的版本或授权。实际字段必须与文件、仓库和用户决定核实。

## 2. 文件模型与入口 <a name="files"></a>

下列位置是默认布局；实际 docs 入口从根 INDEX 解析，内部位置由 docs INDEX 登记。交接各件的根内相对路径以自身 root 为基准，Markdown 链接仍按链接所在文件位置解析。

| 件类 | 默认位置 | 内容与生命周期 |
|---|---|---|
| 当前交接 | 根 HANDOFF.md | 当前现场、事项、需求、依赖及必要入口，随授权维护 |
| L1 世代概述 | 根 HANDOFF-HISTORY.md | 每世代概述及 L2／L3 指针，只追加 |
| L2 版本索引 | docs/handoff/HANDOFF-HISTORY-INDEX-<世代>.md | 该世代一版一行的正式落版索引 |
| L3 阶段／完成卷 | docs/handoff/history/HANDOFF-HISTORY-<起版本>[-<止版本>][-part-<n>].md | 实际阶段状态与正式完成登记，当前卷可追加，封卷只读 |
| 待定记录 | docs/handoff/HANDOFF-HISTORY-PENDING.md | 未排期、挂起或未授权处置的细节，不分卷 |
| 坑位附录 | docs/handoff/pitfalls.md | 可复现环境问题及证据，按需按主题分卷 |

不另建每版本一份的现行交接。历史三层、待定记录和坑位附录只在有实际内容时建立；初始化完成不自动生成落版历史、备份或空卷。

docs INDEX 登记实际形成的文档入口。HANDOFF 的 history 未形成时为 null，不能指向不存在的文件。首次阶段归位可先有 L1 和阶段卷，不伪造正式 L2 行。

## 3. 元数据与工作区生命周期 <a name="meta"></a>

### 3.1 当前交接元数据 <a name="fields"></a>

```yaml
---
doc: handoff
workspace: null
root: null
version: null
status: 待开工
branch: null
updated: null
history: null
---
```

上例是待填写的包内模板，不是已经成立的实例。讨论、澄清和章程拟稿留在会话；用户准入后，按文档授权集中写入章程及必要配套，首次生效状态为待开工。未填写身份、根或目标号的材料不能当作已生效现场，也不另设未初始化、初始化中或其他准备状态。

| 字段 | 唯一职责 |
|---|---|
| doc | 当前交接固定为 handoff |
| workspace | 用户确认的工作区名称，不要求等于文件夹名 |
| root | 实际工作区根绝对路径；只表示路径基准，不授予根身份 |
| version | 当前工作集已准入的目标版本；章程生效时填写，待开工不表示版本已经完成。包内占位可为 null |
| status | 工作区生命周期，仅为待开工、开发中、已落版；事项进度和工作模式另按各自规则 |
| branch | 所属仓实际分支；尚未建仓或未识别可为 null，明确无Git记“—”，不预填计划分支作事实 |
| updated | 本件实际最后维护日；未采用模板可为 null |
| history | 已存在L1的根内入口；尚无历史时为 null |

不设initialized或替代的准备完成开关；接手依据用户准入记录、实际根、当前章程、配置、事项和现场。现有文件中的fieldcase初始化标记不决定接手、重建或施工；下次获准修订时按本模型移除，历史和采用原件不改。自治实现中另有已准入定义的同名字段，按其权威办理。

locale和governance_adoption从config取；官方核心及模块来源不由本实例version代替。接入路线、源／目标、复制清单、工程进度和授权记当前快照及E，不新建初始化文档、消费日志或重复路径配置。

确有适用上位要求时，在本区交接元数据补shared_layer及root_governance，分别记录实际采用的上位共享规范基线、实际继承的根治理代次；根自身是否省略后者按其上位定义。取值须有可核对依据，不照抄现场示例、不以本地版本或官方核心号代替，不为补号读取无权访问的上位私有交接。无该要求时不向通用模板预填部署值。正文资料表仍记实际资料来源；同一治理依据的记录不得互相冲突，资料pin不替换现行管理规范。

### 3.2 三态与转换 <a name="state"></a>

| status | 场景与转换条件 |
|---|---|
| 待开工 | 已准入章程及必要配套已落盘，当前工作集的具体任务尚未开始；首次采用及后续新一轮均可出现 |
| 开发中 | 已按有效授权开始本轮具体工作，尚未完成正式落版；环境配置、依赖安装、复制迁入、建仓／提交及业务实施均属具体工作 |
| 已落版 | 本版已完成适用验收及明确落版放行，并落实该版实际提交／快进、备份、历史等收口要求；无Git按已准入口径如实核对 |

```text
类型：状态机｜工作区生命周期
待开工 → 开发中 → 已落版
   ↑                 │
   └─ 下一轮待启动 ──┘
```

已落版后若下一轮尚未决定，保留已落版及真实版本；新一轮章程获准落盘且具体工作尚未开始时为待开工。已开始具体工作则如实记开发中，不为凑齐阶段强制回退、另停一轮或重复写中间状态。已有版本未落版时，暂停、阻塞、任务完成待审或转讨论均保持开发中，用事项状态和D说明未尽，不退回待开工掩盖本轮。

生命周期不授予施工、提交、备份或发布权限。只有文档授权时停在待开工；同次明确授权已包含后续具体工作时，按范围转开发中接续，不重复索取已有授权。集中写入不保证跨文件或跨仓原子；不凭状态字样宣称必要文件、复制、仓库或验证已经完成。

首版建议从0.1.0.0开始，由用户在章程准入时确定；本轮建设与后续同版任务使用同一目标号，不另设“初始化专用版本”。版本、分支和首次提交取#branch、#release；层的内容身份取D:index-spec#identity，不由工作区状态自动生成固定消费基线。

上位对同名status仍限定其他含义或枚举时，先确认三态的适用关系；不增另一状态字段规避、不把方向1改作自治。未确认的依赖保持缺口，不能宣称真实接入通过。

### 3.3 建设中断需要留下的事实 <a name="init-resume"></a>

只在既有交接记录必要认识：授权来源与仍有效范围、已确认方案、目标版本、源／目标、已完成与剩余步骤、复制依据、实际文件及各仓提交、阻塞和恢复条件。复制、治理对齐、建仓和核验分别记事实；默认源区保持，强制移动的源处置另记。INDEX、config和治理已有权威值的，从原处读取，不全文复抄。

只接续尚未完成的事项，不重建已有仓、不重做已完成提交，不把缺字段或残留initialized作为重新初始化的理由。若章程写入未齐，核准后补齐文档；若实际工作已开始，保持开发中并记录真实未尽。暂停或转讨论后的施工恢复仍须明确执行；无写入权的答案和草稿留在会话，只复用可靠取回的内容。

以下编号与名称固定，便于跨文档定位；其余项目私有小节可在固定骨架之后接续，不改变 §1、§2 和 §3.1–3.6。

```text
   3.5 E. 当前版本需求
   3.6 F. 后续版本登记
4. 治理硬规则
5. 覆盖与落版说明
6. 历史索引
```

### 4.1 两级任务表 <a name="tasks"></a>

版本任务总表：

| # | 版本 | 主题 | 来源 | 状态 | 优先级 | 依赖与边界 |
|---|---|---|---|---|---|---|

需要拆分当前单元时使用当前事项清单：

| # | 唯一标识 | 事项 | 状态 | 依赖与边界 |
|---|---|---|---|---|

两张表都用表格，# 各从 1 连续编排。版本总表记大盘；当前事项清单只拆当前推进单元，一层保持同级。没有需要拆分的内容时保留空表，不造占位任务。

现行工作集只留当前依赖和未尽。旧版本按 major 家族概括并指向历史；已结事项、完成过程及退出本版的旧细节按 #hist 归位。不能因一节有关键句而整节保留。

### 4.2 快照各段内容 <a name="snapshot"></a>

| 段 | 放什么 |
|---|---|
| A | 实际路径、版本／分支、仓库布局、Git 能力、提交／落版／备份状态、关键服务与端口、只读资源、资料依赖及恢复入口 |
| B | 必要触发与行动判据及入口；问题、根因、修正、复验和证据按 #pending-pit 入坑位附录 |
| C | 用户已裁定内容、理由与依据；候选建议不得冒充裁决 |
| D | 按优先级列仍需用户决定或授权的事项及其影响 |
| E | 当前版本唯一可验收目标、来源、范围、落点、依赖、边界、完成条件及验收入口 |
| F | 已登记但未进入当前范围的后续主题、来源、依赖、边界及必要指针 |

§4 只留当前行动必需的判据与权威入口；长期职责、权限、红线与工作方法拟入本区治理，有效设计指导的内容、分流、参数单点维护及提炼取 D:design-spec#scope、D:design-spec#split、D:design-spec#use，按准入归本区 DESIGN，操作细则引用所属规范或知识入口。一条约定明确一处维护权威，目标载体建立与迁移须先准入，不预建空件。§5 记实际提交、覆盖、日志／备份和发布口径；§6 记实际历史入口与检索方式。

用户点验的详细操作在会话中给，HANDOFF 只留状态、结论、证据去处和缺口；不把长操作清单反复塞进当前工作集。

### 4.3 现行交接体量 <a name="size"></a>

每次换版完整重读本区现行 HANDOFF，报告含元数据的完整 UTF-8 实际 B 字节数；随正常拟稿按下表提示。

| 触发 | 提示 |
|---|---|
| 换版时 ≥50,000 B | 提醒用户安排一轮 HANDOFF 的 MVD 量化与清扫 |
| 达到 90,000 B | 预警，报告主要占用及旧内容归位、合理分版建议 |
| ≥100,000 B | 每轮拟稿均告警；回落后按实际体量提示 |

这些是现行交接的告警阈值，不拒绝记录必要事实、需求、边界和验收，不强行分版。清扫按 #cleanup，分版以可独立验收的完整交付为据，真实未尽、待审与发布状态保持；历史卷和坑位附录的分卷规则另取 #hist。

## 5. 事项身份、状态与展示 <a name="items"></a>

### 5.1 唯一标识 <a name="item-id"></a>

- 无既有稳定键的事项用 `<事件类型>-<流水号>-<短名>`。事件类型用符合本区业务的短前缀，可以扩展，所用类型的含义在本区交接登记。常见示例有 `ini` 初始化、`cre` 创建内容、`fea` 新增能力、`fix` 修复、`cho` 治理维护、`sub` 子任务。
- 同一 major 内各类型共用一套流水，从 01 依次发号。01–99 用两位，随后为 100、101 等。类型和流水号的组合承担唯一性，同一 major 内已发组合只对应原事项。换 major 可从 01 重开，跨版延续的事项保留原标识，新号避让仍在使用的组合。
- 短名用少量词或可辨识的缩写，能辨识事项即可。长度上限为 20 个字符，含内部连字符。超长须改写，不机械截断。
- 同一事项不因改名、排序、换表、状态或版本迁移改变标识。名称和唯一标识均不能在同一现行清单重复；已用身份不得复给另一事项。
- # 只供本轮扫读和点验；持久引用用唯一标识，跨区补工作区，历史定位补版本。已有版本号等稳定键的表不重复增列事项身份。
- 迁移旧编号时，记录原版本／表位置到新标识的映射；历史原文保持，不全库改号。

### 5.2 状态表 <a name="status"></a>

状态列以以下标记和简称开头，一个事项只用一个；后接必要细节。本表管理事项进度，不替代#state的工作区三态；单项完成、阻塞或待审不自动切换生命周期。

| 写法 | 含义 |
|---|---|
| ✅ 完成 | 约定的完成条件已满足，依据须可核对；需人工点验的事项，须由指定验收人确认通过后才记完成 |
| 🔄 推进 | 正在推进 |
| ❌ 否决 | 未通过或被否决 |
| ⚠️ 阻塞 | 有具体缺口，待处理 |
| 👀 待审 | 已有产出，待用户或其指定的验收人审阅；需人工点验的事项，自检通过后先记待审 |
| 💡 待决 | 待讨论、裁决或发令 |
| ⏸️ 暂停 | 已暂停或延后 |
| ⬜ 未启 | 尚未开始 |
| 🧊 冻结 | 不展开；同行必须写“解冻：<可判定条件>” |
| 🗑️ 废弃 | 不再推进，按本版归位 |

冻结持续到条件达成，不因换版解除，也不逐版追问。达成时提出判据交用户确认，默认建议待决；条件不再适用时提出废弃。落版前核对全部冻结条件，未达成只留数量汇总，已达成或不适用的完成用户裁定与记录后再收口。

### 5.3 列表、重排与快审 <a name="review"></a>

- 列版本任务、当前事项、待办时分别取对应表／段；事项同时显示 # 和标识，不另造展示编号。
- 未有唯一标识时先拟迁移；重排先完成项、后其余项，各组原相对顺序保持，# 连续重编。与快审组合时，完成项仍保持原序，其余按点验前置、依赖和收口顺序排列；无依赖者保留原序。
- 快审默认采用现行 HANDOFF，用户指定拟稿时采用对应拟稿；只取来源 §2 未完成项，包括暂停、冻结和废弃，不从 F、历史或其他节补入。保留边界和恢复条件，列出不表示恢复。
- 快审和人工审计子表沿用所采用现行或拟稿表的 #，允许断号，不另编号，并标明来源；F 项无 §2 号时记“—”。
- 先展示完整拟重排表，再按同序做快审；人工点验提供对象全名及类型、实际入口／定位、操作、通过条件、未测与已知缺口。相同前置只写一次，关联验证可说明覆盖关系。
- 冻结或废弃项没有待核处置时只列状态，不强加人工审计；有待核处置时明确剩余核对内容。
- 入口未核实须明确标缺口；不能让用户猜目录、搜交接或自行补操作。表格／列表表达取 config.review.layout，但任务总表、事项表和重排表始终是表格。

## 6. 一个版本的生命周期与判级 <a name="life"></a>

### 6.1 最小完整目标 <a name="scope"></a>

E 只写本版可验收的完整目标。下一版按实际反馈确定；F 只记后续，不自行提前讨论、设计或施工。用户主动讨论未来项也不自动纳入当前授权。

范围外新增字段、能力或规则，先列“项目／现在不做的实际影响／建议去处”，由用户决定本版、后续或不做。现状断言先核实；推测的未来痛点不当作实施依据。

避免预制无人使用的抽象层、运行时、权限矩阵、并发编排、迁移脚本或资料文件；已经明确要求的语言、层、模块与验证不得以精简为由删除。

治理拟稿先按 #rules 做 MVD 量化。体量是观察值，保留必要判据、边界、去处、异常与恢复条件。

### 6.2 版本对象与递增 <a name="ver"></a>

本实例版本、官方核心来源、每个已采用模块来源及各资料层版本分别维护。config.fieldcase_version 和 modules 的来源字段记录所采用的版本。实际比较基线从 D:upstream 的现行采用入口取用。普通本地定制保留原来源。

本实例采用四段 0.<major>.<minor>.<patch>；首段 0 表示尚未定型，不参与判级。末段为 0 时可省写但须能唯一对应；登记时建议四段写全。

| 档 | 判断 |
|---|---|
| patch，第四段 | 修补、澄清或更正已有做法；增加约束；数据或参数取值变化但做法不变；仅跟随重 pin |
| minor，第三段 | 新增消费者可采用的能力／模式，或取消既有做法；消费者需要学新做法才能用 |
| major，第二段 | 分区、路径基准、元数据、版本／pin 机制等结构变化，或改动本递增尺度 |

节号、标题、字段名、路径、命令或清单项等仅发生位移或改名并使既有指针失效时，按 minor 判级。变更本身符合上表的结构变化判据时，按 major 判级。两种情形均同步有效引用。判级看行为和结构，不看行数。

只有能指出错误记录依据、且改动完全处于开头元数据的勘误，可独立记录而不铸产品版本；更换实际依赖不是勘误。私有治理的独立维护按根治理处理，不因此要求产品重新落版。正文／行为的产品变更按其实际影响判级。

### 6.3 仓库与分支 <a name="branch"></a>

适用方式取本实例根治理的已选规则，不每轮重新选择：

| 方式 | 行为 |
|---|---|
| 分支研发 | 新仓按下文建立共同起点；本轮实际研发使用dev/<本轮版本>，预览pre/<主题或版本>。版本分支存在期间main保持起点或上次落版，正式收口才ff-only快进 |
| 直接维护 main | 按授权直接维护main，无旁支快进环节；不声称同时具备正式目录稳定、同仓worktree隔离开发的完整方案 |
| 用户自定 | 先明确分支名称、用途和收口规则，再按已确认规则执行 |

建仓与首提交属于开发中。对本次准入、确无历史提交的本区新仓，完整方案须列明根、署名、主干起点、首提交范围和后续分支：可先在main提交已准入章程及该仓必要文件作为共同起点，再在实施后续任务前建立dev/<本轮版本>。两者使用同一首版号；起点不是单独初始化版本、初始化完成标记或正式落版，不默认创建专用完成标签。

该操作须有建仓及提交授权；只有文档授权不执行Git。已有有效HEAD、源仓、父仓、外部共享仓及原位升级不套用新仓起点规则；同次中断先核对现场，保留已有提交和固定标签，只补剩余步骤。有适用上位约束与本方案冲突，或有权主体明确要求确认时，停止受影响Git链并提裁定；已有明确授权不重复申领，不借新仓规则豁免主干保护。

版本与固定定位按实际所属仓和内容来源记录。外部共享层按原仓和版本消费，T 不另建仓。迁入仍先复制获准业务内容、按准入方向核对治理与入口，再目标原地建仓；章程准备不代表迁入已完，也不提前建立空底座仓。旧源历史按授权留作来源，不与新实例版本混同。T中worktree仍属对应原仓，无共同历史不能直接ff。

开发同号可累积多次提交，不要求每提交一次升号、推进main或通知全部工作区。已供消费的提交保持可达，固定标签不移动。需要固定消费基线时，另核内容完整性、准入和实际定位，不因首提交自动产生stable_ref；分支名不替代提交定位。

`pre/<主题或版本>` 仅用于预览。预览保持工作区版本号，不办理落版，预览分支永不合入 `main` 或研发分支。获准保留的成果在研发线上重新落实，预览分支的存续与删除由用户授权。维护旧版、合并／重放、重置与删除分支仍须相应授权，不能因修复紧急绕过门槛。

### 6.4 开版、提交、落版与发布 <a name="release"></a>

1. 在会话收敛本版目标、范围、依赖及完成条件；用户准入后，按文档授权写入目标version和E，首次生效为待开工。当前实际分支照实记录，未建仓不虚填。已有仓的文档准备须在获准位置及分支进行，不旁路推进受保护main。
2. 用户明确执行且开始具体工作时转开发中，使用同一目标版本，按已选方式建立研发现场；无Git如实登记。开工所需缺口未清除时报告并保留未尽，不凭已填版本号执行。
3. 在授权内实施、验证、修复、复验，按明确路径提交；他人改动不代提交，不全量暂存。阶段完成、返回讨论或等待审阅不自动退回待开工。
4. 交用户验收；开发完成或阶段 Goal 结束不等于落版。落版须已有用户验收及明确放行；提问选项写有「落版」，或用户点选含「落版」的选项，均不构成落版放行。
5. 按 #check 收口；分支方式不能 ff 时停止交用户裁定，不擅造合并提交、重放或重置。
6. 公开发布另按实际授权和已核实官方入口办理；不能用本地落版说明已经对外发布。

追加：用户声明的版本含“追加”时，先核对本区实际版本，不一致停止并询问。一致且已启用 Git 时，在同版本内使用 git commit --amend 并重写累计提交信息，按既有授权覆盖同版备份并核对一致。已供消费的提交须保持历史可达，稳定标签不改指向；不能同时满足时先交用户裁定新提交或新版本，不静默改写固定定位。多版本任务按序逐版实施、验收、提交和备份；普通开发追加提交不等于本模式。无 Git 时如实说明不执行提交动作。

## 7. 资料依赖与实际 pin <a name="pin"></a>

消费区 HANDOFF §3.1 的一处资料依赖表，一层一条，合并承载 pin 与实际消费事实：

| 层 | 采用方式 | 内容版本 | 固定定位 |
|---|---|---|---|
| K | 开发 | <所选 INDEX 的 layer_version> | <确定的开发提交 ID> |

采用方式可为开发、正式、候选试用；外部共享层沿实际内容版本和固定来源，不虚构其缺少的初始化元数据。来源无可靠Git／副本定位时写本地现状和保障限制，不因本区无仓否认独立来源已有提交。各来源按实际内容版本分别记录。联合升级时说明本次实际组合。

候选试用在同一位置补充层／稳定标识范围及原正式版本／固定定位。比较审阅不改变 pin；结束试用恢复原依赖，或经准入采用新稳定基线。候选正式化可复用验证，但核对最终差异。

资料层 INDEX 描述内容，不记消费者；config 只管默认策略，不另复制实际依赖。接续读取按表恢复 INDEX 和正文同一来源，不能悄悄跟新。固定来源不可取得时报告缺口，不把当前 main 或搜索摘要当作替代。

恢复旧现场涉及实际适用的上位治理时，从该版经核实的交接记录取 `shared_layer` 与 `root_governance`，按有权入口回查当时的治理依据，并核定其与当前适用规则的关系。来源有 Git 时，在实际来源仓按真实版本登记文件及版本值检索引入该版本的提交，例如用 `git log -S`。确认提交与原记录相符后，在获准的独立工作树或仓库副本中 `checkout` 到该状态核读。来源无 Git 时按原登记回查固定原件。依据无法唯一核实或有适用冲突时，报告缺口并暂停依赖该依据的恢复。

## 8. 当前内容的保留与归位 <a name="cleanup"></a>

逐段按当前及已明确后续依赖判断：

| 痛度 | 处置 |
|---|---|
| 致命 | 移出即无法继续、须通查历史重建的必要认识原样保留 |
| 重要 | 当前关键细节仅作无损压缩 |
| 常规 | 可概括、合并或进历史，按实际需要留指针 |
| 无关紧要 | 有溯源价值进历史，无价值删除 |
| 挂起 | 细节入独立待定记录，当前只留标识、状态、一句及入口 |

职责分流：当前必需的现场、未尽、判据与裁决留现行交接；已结事项、旧需求、完成过程和旧版本明细按 #hist 归历史，未排期细节入独立待定记录并留必要入口。坑位、设计指导、长期规则与操作细则按 #snapshot 分流；目标载体的建立与迁移仍须准入，必要内容保持可达。

量化按五类痛度分别列五张表，逐项列定位、当前依赖、建议、前后 B 与去处；后值用完整稿计算，未拟时标未拟。可从指针定向取回的不算认识丢失，不用“曾经重要／将来也许有用”替代实际依赖。

归位不改变裁决、冻结、验收或发布状态。已有归档不重复搬运；机械分卷只读标题边界和必要元数据，由工具按原字节搬运并比对，不把整个历史重新交给模型复审。

## 9. 历史三层与附录 <a name="hist"></a>

### 9.1 L1 世代概述 <a name="l1"></a>

元数据使用 doc: handoff-history、workspace、root、latest、count、updated、current。latest 为最新已正式归档版本，无则 null；count 只统计有号的正式归档版本。阶段归位不虚增。

每世代一节：一句定位、该世代实际增量概述、L2 入口及所需卷指针。世代取版本前两段，例如 0.1。L1 不承载完成登记全文。

### 9.2 L2 版本索引 <a name="l2"></a>

元数据为 doc: handoff-history-index、workspace、root、updated。一版一行，只追加：

| # | 版本 | 主题 | 判据关键词 | 落版日 | 备份入口 | 卷 |
|---|---|---|---|---|---|---|

关键词选 1–3 个最可能回查的症状、文件或规则名。卷入口与实物一致且卷内确有该版本段；没有正式落版不造落版日和正式行。

### 9.3 L3 卷 <a name="l3"></a>

元数据含 doc: handoff-history-archive、workspace、root、scope、archived、frozen。scope 写实际覆盖范围；archived 为开卷日；frozen=false 可追加，true 封卷只读。

卷按最大适用单位组织，不跨 major 混装。卷体积按含元数据的完整 UTF-8 字节数计，同一单位预计超过 100,000 B 时才依次降为 minor、patch、part 分卷。开放卷止版本未知时不写止号，封卷不改文件名，实际区间以 scope 表示，保持旧指针有效。

阶段记录和正式完成登记均追加到开放卷。本卷所承载的分卷单位结束，或卷的实际体积达到 100,000 B 时，将 `frozen` 设为 `true`，此后只读。后续有实际内容需要入卷时再开新卷。

开发阶段内容标版本、开发中和来源；不能套“已落版完成登记”的声明。正式完成登记追加需求原文、落版与备份、本版要点及既有阶段记录定位；不重复复制已归位正文。

历史进卷清除状态 emoji，保留原简称与措辞。归档后的事项状态以原简称为检索键。不得借归档重写历史判断。卷及索引受所选仓库控制与必要备份覆盖，不落到忽略目录。无 Git 时说明缺少仓库历史保障，仍保存可达文件。

早期无版本事实按原日期范围形成只读日期卷，不推断版本、不混入版本卷、不为其造 L2 版本行；L1 给概述、关键词和可考备份锚。日期不可考时标明依据缺口，不编造。

### 9.4 待定记录与坑位 <a name="pending-pit"></a>

待定记录元数据用 doc: handoff-pending、workspace、root、updated；按标识组织，不分历史卷。F 只保留必要入口，用户点名或实际依赖出现时定向读取，不常态展开全部未来设想。

坑位附录用 doc: handoff-pitfalls、workspace、root、updated，不承载版本。B 段留不看附录也能正确行动的判据，证据放附录。编号稳定只增不复用，B 第 n 条对应附录 pn；有坑才建，尚无证据时写明现象与缺口。

附录按主题只追加，纠错用补充，不抹除既有记录；单件超过 100,000 B 再分主题。入受控记录前去除令牌、cookie、内网地址、真实邮箱、真实个人地址和无须留存的敏感信息。可复现时间戳保留以判断证据新鲜度。

### 9.5 回查顺序 <a name="find"></a>

先读 L1 元数据及世代标题，再找 L2 版本行，最后只读命中卷的小节；无精确版本时按关键词跨入口检索。待定与坑位按标识／关键词定向取用，不整读所有历史。排查重复现象时，用同一现象、错误码或关键词核查现行 HANDOFF §3.2 B 和已登记的 D:pitfalls 附录，再按坑号定位。

当前引用要在归位时更新到实际历史小节；历史原文按当时路径读，不批量改写。移动前后机械比对原文，索引和引用同批验证。

## 10. 落版核对 <a name="check"></a>

### 10.1 落版提交前 <a name="pre"></a>

- 当前 E 的来源、范围、边界、依赖、验收可完整回查，阶段记录入口有效。
- 实际仓库根、branch 和版本与交接相符。分支研发用 `git merge-base --is-ancestor main dev/<本轮版本>` 核对祖先关系。将占位符替换为 HANDOFF 中的实际目标版本，例如 `git merge-base --is-ancestor main dev/0.1.0.0`。退出码 0 才通过。分叉或无法核实时停止并交用户裁定。自定分支按已准入收口规则核验。
- 用户已验收并明确放行落版；候选待审、主干起点、固定消费基线及开发提交均不冒充正式完成。
- 当前任务表、事项状态、未尽、已决、资料依赖和必要日志已一致；日志用本项目已选去处，不为清单新建多份日志。
- 冻结项已按 #status 核对；相关活跃协作记录若已安装对应模块，按其规范完成本区必要处置，不扫描无关历史。
- 有效引用可达；版本与状态元数据已同步，临时证据、可发布产物、恢复备份的用途和范围分别明确。

### 10.2 落版动作与随后归位 <a name="post"></a>

- 按授权形成落版提交；分支方式 ff-only 快进 main，直接 main 按其规则，无 Git 明确无提交／快进动作。
- 保存并核对本版约定备份，提交、主干、备份状态一致后才报告落版。
- 正式完成登记进入 L3，并按 #l3 核对封卷条件。L2 追加实际行，L1 更新必要概述和计数，复用既有阶段记录。
- 正式落版后的归档提交属于随后维护／下一版开场；不能把归档尚未发生的事实写成提交前已满足。开发阶段的日常归位不构成落版放行。
- 换版时按 #size 完整重读现行 HANDOFF 并报告体量、必要预警及引用核对结果。下一版尚未获准时，现行交接停在已落版、下一版待发令的真实形态，不凭空开工；对外发布与发布地址另记实际授权和结果。

## 11. 接续与编写红线 <a name="rules"></a>

- 接手与重读按根治理 §1.4 执行；已固定资料来源按 #pin 恢复，不能用会话记忆替代实际输入。
- 交接脱离原对话仍须自足；禁止“刚才那个”“同上”代替目标、依据或入口。记录用户原始授权的必要范围，不能凭 Agent 消息自行授权。
- 在仍有效的文档写入授权内，及时把接续所需的状态、现场、裁决、阻塞和证据去处记入现行 HANDOFF。已知将压缩或换会话且必要内容无法立即成文时，需发令的事项在 §3.4 D、后续事项在 §3.6 F 先登记主题和来源。普通讨论只拟稿，事实写入仍取既有授权。
- 同一事实只保留一处权威记录；其他位置引用。发现冲突先核实并按授权修正，不能为恢复简单而抹去分歧。
- 规范只留当前判据和边界，时间安排、裁定过程与变更沿革放交接事实或历史；元数据、历史理解所需一句和实测时间戳可保留。
- 当前交接、L1、L2 与规范不以加粗替代层级；状态按表。编号逐条分行，不将多项圈号挤在同一行。
- 拟稿、回执和交付中不能夹带不属于既有要求的新规则；未命中项先单列内容、影响和建议交用户裁定。
- 治理拟稿落笔前做 MVD：确认实际保留的判据、边界、去处、异常和恢复条件，逐项做删除测试、无损换短及弱条留存说明。交稿列候选前后实际 B、增删行和占比，未拟后值标明未拟。体量服务于已授权功能。
- 存量治理或历史结构不符合新模型时，先拟迁移范围，保留事实和字节等同依据，再按授权迁移。采用 Git 且获提交授权时，历史迁移在实际所属仓按清单限定路径单独提交，便于回滚本次搬移。不能为了形式整齐丢失仍有用认识。
- 治理入口名称与宿主不同，可按用户准入设指针入口指向同一权威，不复制两份规则；宿主能力必须实测，未确认项保留缺口。

## 12. 权威与复核 <a name="auth"></a>

本规范以D:handoff-spec为本实例交接模型权威，根docs入口定位D总INDEX，由D条目维护实际文件及B，不另建规范别名表。根治理规定权限及文档准入，指南承载操作。本规范复核触发见元数据，修改后同步实际受影响模板、索引、引用与必要验证。
