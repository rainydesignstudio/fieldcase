# DESIGN文档维护规范

入口由根docs到D总INDEX的design-spec条目定位；索引模型取D:index-spec，交接模型取D:handoff-spec，授权仍取根治理。K中的同名文件不自动成为本实例管理规范；已适用上位规范仍按其范围约束。

本规范规定工作区 DESIGN 的提炼、组织、使用与维护；“区”指用户明确指定的消费工作区，不因读取本规范取得根或其他工作区身份。授权和实施沿本区治理；具体设计规范按用户实际登记的来源取用，不强制存在 K:design、某个前端栈、参考项目、设计包或外部 Skill。治理重读仍按根治理全量办理，设计事务的定向取用不减免该要求。

## 1. 内容与适用范围 <a name="scope"></a>

- 区DESIGN首章明确设计对象、类型、使用场景及适用范围；正文只收已准入的设计结论和执行指导，保留前提、关系、方法、行为、边界、例外及设计验收判据，使后续任务能据此作设计判断。
- 设计类型按对象和实际用途区分，同区可有多类设计，不由工具或文件格式决定。例如平面资源围绕视觉表达，界面还涉及交互、组件、兼容、适配、动效和技术栈等实际约束；按对象取舍，不作为每区必填清单。具体设计条文留区DESIGN，本规范不统一各区风格、组件方案或技术栈。
- 影响设计成立的技术或媒介条件可作为设计前提、关系或约定；安装、构建、调试和交付过程按#split 分流。“纯设计指导”保留必要技术依据。
- 有明确范围的具体约定可入区DESIGN，不要求每条适用于全区所有任务。基础方针、限定场景关系和具体参数按实际需要分层定位，不预设各区具备设计包、tokens或相同工具链。
- 设计验收判据表达设计应满足的标准，不是某次验收结果。区DESIGN不记事件、事件因果及取证推导、施工过程、当次实测或验收结果，不附事件标识及溯源链；现行规范和设计资产入口仅用于执行定位。分流时保留设计成立的前提与判断依据。

## 2. 分流与单点维护 <a name="split"></a>

下表载体取本区已准入入口；新建或迁移载体仍按本区治理准入。

| 载体 | 职责 |
|---|---|
| 区治理，如AGENTS.md | 长期职责、权限、红线，以及区DESIGN的读取与维护触发 |
| 区交接，如HANDOFF.md | 当前授权、任务、状态和裁决；B留必要触发与问题入口，C留用户裁决 |
| 区DESIGN | 已准入的具体设计指导、适用条件、边界、例外及设计验收判据 |
| 参数、资产及实现入口 | 维护具体配方、数值、实例、素材、组件或实现能力；按本区实际组织，不整包搬入DESIGN |
| 问题记录，取D:handoff-spec#pending-pit | 问题、事件、已核实根因、修正、复验、证据及完整事件标识 |
| 原任务记录 | 成功过程、原始材料、施工与当次验证记录；裁决按交接职责登记 |

- 一条约定明确一处维护权威，其他位置按必要入口取用；不因内容具体而拒绝提炼，也不独立维护两套条文或数值。检查断言和历史快照不作为另一套规范权威。
- 问题侧按D:handoff-spec#pending-pit归位，保留原有标识和必要历史定位，不另造事件编号制度；未建问题载体时先拟具体路径和正文，准入后建立。成功过程与证据留原任务记录，不为成功强造问题。
- 区交接、问题及任务记录可指向区DESIGN当前条款，区DESIGN不反挂事件链。产物版本、交付、核收职责及资产生命周期等非设计治理沿原载体维护。

## 3. 提炼、消费与持续修订 <a name="use"></a>

- 没有适用设计事务时，不预建空 DESIGN，也不阻塞普通文档任务。首次出现设计需求，先识别对象、场景、既有依据和必要约束；确需新载体时，拟出根内具体路径及自足正文，经原有准入与执行流程建立并登记实际入口，不在初始化问卷增加必填题或设计开关。
- 已有品牌、项目或领域设计规范时先接入，保留其适用范围和参数权威；不整份搬运，不以新建 DESIGN 覆盖已有用户定制。
- 设计事务开工先从本区已准入治理或所属索引定位区 DESIGN，读取内容边界和适用条目，再取相关资产或实现入口；具体选择与任务锁定项按本区治理确认。
- 存量提炼综合获准范围内的现行治理、设计资产、实例及任务记录，主动识别可复用方针、场景关系和缺口，不以已发生问题或用户举例为清单上限。必要历史按D:handoff-spec定向取用，不因来源在历史而排除有效约定，不全量漫读历史或源码；须实际读到足以判断的内容，证据不足列缺口。
- 区分用户明确裁定、现行有效规则、已核实问题及修正、已验证成功做法和实现能力。失败现象不直接升为通则，单次成功不自动成为全区默认；从资料中归纳可复用的关系、方法与成立条件，保留场景差异，不把一次修补常数升为全区参数。
- 施工、修缮、验收或交接清扫形成新判据、旧规则修正、边界或例外时，在已有获准记录或回执中提出候选，不等整版落版，无新结论不凑条目。用户准入后更新区DESIGN和必要当前引用，业务验证不替代文档准入。
- 后续任务按已准入条款消费与验证，出现反证、复犯或前提变化时再拟修；仍有效的规则不因暂未使用而归历史，失效或被替代内容沿本区清扫规则处理。交接清扫取D:handoff-spec#cleanup、D:handoff-spec#rules，迁移后保持必要入口可达。

## 4. 审阅、验证与共享适配 <a name="review"></a>

- 审阅材料按设计问题归并，用可直接判断的文字列出“来源定位—候选指导—适用范围—维护去处”。需用户裁定时说明待决内容、选择及影响，来源指针用于核实，不替代待决正文；询问方式沿本区治理和用户当次要求。
- 对已裁定的提炼事项，归并时逐项核对用户最终答复，保留原采纳内容、后续补充及排除项；不以摘要或落位表替代原裁定。
- 治理变更交完整拟稿或diff及D:handoff-spec#rules的MVD量化；溯源材料留审阅或已有记录，不进入区DESIGN，不另建固定账本。点验内容边界、获准范围内的指导是否可用、缺口是否明示、分层与单点维护、入口及读取和沉淀能否接续。
- 验证按任务阶段、设计对象及目标场景选择：视觉结果观察实际呈现，界面设计检查适用的状态、操作与适配关系；代码、算法和度量辅助判断，不能替代相应观察。文档核验、作品或实现复验、用户验收分别记录，未具备条件或未测的内容明示，不以文档通过代记实际结果通过。
- 区 DESIGN 中具跨工作区复用价值的指导，可先向用户提出上升建议；是否形成共享规范、由谁审议及其实际入口由实例用户决定，不强制存在 K:design。已采用跨区协作且本次发送获准时按根治理办理；未采用或无通信能力时交用户可抄送建议，不以本区准入代替共享准入。
- 区DESIGN由所属区按用户授权维护；本规范的修订按本区根治理的文档准入和采用边界办理。跨区反馈提炼、组织、适用和验证方面的共通缺口，具体设计条文不因区内准入自动进入本规范；各区按实际采用版本接入，不因共享层出现新稿就自动改写本区规则或pin。
