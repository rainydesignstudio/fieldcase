# 层与模块采用配套

本件保存可选K／R／M材料、三模块的安装目标、必要差异及核验说明。日常权限取根治理，操作复用D:agent-guide；下面条文只有在用户选择、完整方案准入和明确执行后才应用。

## 1. 兼容范围与共同收尾

- 本轮核心为根入口＋D＋T，规范统一在D/spec，不维护根rule-*别名。K／R／M按实际需求采用，不写入config.modules；专业、自选和极简仍由用户确认，不从包的默认空数组推定已选极简。
- 配套材料的版本与来源取同目录分发 INDEX；整包批次取同一固定资源根的随包 README §1。同号不同结构不推定兼容。旧原件、原始测试和固定来源不迁位、不倒改，新增行为未实测。
- 三模块knowledge-acquisition、cross-workspace、unattended的方法规则可在D＋T基础安装；正式知识产出另需已准入K目标。安装不自动创建K、抓取资料、通信、建立Goal／heartbeat或宣称运行能力已验证。
- 采用前从固定包留存原件，旧实例比较旧原件／当前定制／新原件，核本批恢复依据：Git覆盖足够则复用，缺口补文件快照。不会因材料齐备改采用方向、现有版本、源号或权限。
- 实际工作规范只装入本区D的专用spec目录，由D总INDEX维护入口、类别和B。未选规范只留材料，不登记为生效；所有示范B在最终采用内容重算，现行条目接续编号，稳定标识不改。
- 不提供外部Skill、特定工具实现或业务库作为基础依赖；项目内Skills尚未提供，不把全模块解释为存在未提供封装。

## 1.1 规范安装与继承

方法规范放在D:index-spec所在的本区专用目录，D总INDEX登记cache-spec或contract-spec的真实入口、规范类型和B，不另设根别名或D仓／层号。实际目录不固定为文中示范字面路径，工具参数先按根docs和D条目解析。

已有上位模式按原权威继续适用，不因共享K有同名文件记为本区模块已装；与拟装规则同名或存在适用冲突时先说明并提有权方裁定，不覆盖上位定义。未选K不取消任何已生效上位规范。

共享K／R／M／T保原维护权，本区操作配套写本区根治理；正式产出进入共享K仍须所属维护者准入。共享T只复用实际合法分类及归属，不复制空INDEX覆盖上级、不新增公共分类或第二T；实际所需依赖缺失时不冒记相应能力就绪。

## 2. 可选K／R／M

### 2.1 安放与根入口

只将所选自建层的原件复制到获准目标，K材料由分发索引knowledge-governance／knowledge-index定位，R／M由原标识定位。导入已有知识库先核原结构、内容索引、许可和范围；引用共享层只登记真实入口，不覆盖源治理或总索引。

根表已有docs和T；把实际选择的K、R、M放在T前并按当前表连续重编号，D不增加另一行或独立仓。完整专业布局的新增行示例如下，只选一部分时仅加入对应项：

```markdown
| 8 | <a id="K"></a>K | 知识库层 | 索引 | [K索引](knowledge/INDEX.md) | K:<标识>按本层实际协议取用知识，规范效力沿实际准入范围 |
| 9 | <a id="R"></a>R | 参考层 | 索引 | [R索引](references/INDEX.md) | R:<标识>读取固定参考及证据，不改源快照 |
| 10 | <a id="M"></a>M | 材料层 | 索引 | [M索引](materials/INDEX.md) | M:<标识>定位治理和已准入生产材料 |
```

R不新增AGENTS，K／M的维护规约只在实际自建或明确采用时生效。D三核心规范不复制到K。未选层不登记可消费入口，不为默认专业之外的极简或自选强建空目录。

### 2.2 保护、仓库与事实

D核心及专用规范目录常态受保护。资料层的layers／targets按根实际入口、已采用治理／规范及完整目录生成；无资料层可同时为空，确无适用目标时说明依据，不能漏掉真实已生效对象。目录身份和B按本区七列或外部真实协议核对，保留用户获准自定义目标，不预设K:specs。

Git 动作按开发中的获准任务办理，取已准入方案的实际仓根与受控路径清单。D 随本区维护，T 不独立建仓，外部仓保持。忽略按实际入口和跟踪范围派生，保留应受控文档。

旧实例不因K改为可选就卸层、删知识、迁.git或重置历史／版号。只有原K无需继续采用且清单、引用、仓库历史和恢复方案均明确，才能另按授权退出现行；否则保留K，仅迁移获准管理规范及引用。工作区迁入仍先复制业务、核治理，再目标建仓，不提前建空底座仓。

### 2.3 核验

分别核D必需文件、所选资料层入口、实际资料和协议、完整保护、治理B及权限；选Git才核真实仓根和提交。只做静态检查就记静态，不冒称资料已导入、共享接入或运行能力已实测。

#### 2.4.1 讨论：联络

- 用户明确目标既有会话后，仅授权本次简介或非执行回执发送；有已拟内容则按该范围发送，其余介绍绑定工作区、Agent 身份、目的并请对方确认收讫及需同步信息。
- 不发送执行任务，不写入文件；执行推送按 §2.4.2–§2.4.3。目标不明先澄清，不自行扫描后向所有会话联络。
- 发送与实际收到回执分别报告；工具不可用时交可抄送文本，明确未发送。收到对方消息不授予自动回复权。

#### 2.4.2 执行：推送

- 用户明确目标既有会话和本次执行任务后，按 §2.3 的自足任务包发送，写明绑定工作区、Agent 身份、可核对的用户原始授权、范围、待审门槛及回执要求。
- 本方式只授予本次发送，不自动进入多会话调度。接收方按自身治理核对原始用户授权、范围和写入条件；建议仍为建议，文件、版本、验收和发布归所属主体。
- 目标或范围未明先澄清；报告实际送达、回执及缺口。能力缺失时交可抄送包；重派、追加发送或周期跟进须有对应授权。

#### 2.4.3 执行：推送至新会话

- 用户明确新建会话、目标工作区及执行任务后，按 §2.4.2 组成任务包，作为新会话初始消息创建，并报告实际入口或未完成状态。
- 权限只含本次会话创建和任务传递；目录、仓库、worktree、子代理和外部服务不随之获准。不得用其他类型的执行单元替代用户指定的新会话。
- 创建失败或仅排队时按真实状态报告，不把临时标识当已就绪会话，不重复创建来掩盖未明结果。

#### 2.4.4 多会话执行

- 用户明确切换，且本区实际具备创建或派发能力时启用；先明确 Manager、Generator、各目标工作区、任务边界及允许的执行单元，记录实际会话／代理和调度状态。
- Manager 负责方案、派工、提交前内部检查及获准提交／备份；Generator 只实施指定范围，自测、修复并交改动、验证、未尽及证据去处。角色不获得他区写权，提交、备份、落版和发布沿原授权。
- 同一工作区同时只有一个会话修改文件，交接写入持有者后再接手；不同工作区也只按各自权限操作。新建用户会话与子代理分别核对授权，不相互替代，不因工具可用默认并行。
- 自动派发、跨会话回执、重派和必要等待只在本次明确调度范围内办理；接收方核对用户原始授权，回执要求不替代发送权限。范围外任务、他人会话及新的持续调度不自动获准。
- 没有实际机制时保持未启用并交人工任务包，不虚构派发或完成；切回普通执行或人工调度后，自动调度停止，未尽任务和子执行单元按用户授权如实收尾。

本组模式以本文件 §2.4 为权限权威；复核触发：通信／调度能力、目标绑定、用户授权接口或协作职责变化。契约结构与生命周期取 D:contract-spec，不把契约当作执行授权。
```

现有 §2.1 指令组合规则继续有效；“回执＋联络”只允许发送其中已准入的非执行内容，执行任务仍按明确推送办理。本模块不接入根专属同步、子工作区批量治理或任何契约覆写例外。

### 4.3 核验

核对本区实际采用的模式名称、入口与定义，人工调度和普通执行边界保持；核D:contract-spec、D:index-spec真实D条目、B、规范目录完整成员及合法T:contract入口。上位继承模式按原定义，不冒记本地安装。通信、建会话、子代理及跨区写入须分别核授权，不以安装成功代工具实测。

实际通信测试须另定授权目标、原始任务及回执范围；未做时标未测。不得为验证随意向现有会话发消息，也不把可抄送文本记作送达。

- 宿主提供 Goal 时为本任务保持一个 Goal，循环实施、验证、修复、复验；完成条件含滞留项清零才标完成。Goal 或 heartbeat 的创建、复用、检查、暂停缺失或失败时，记录实际状态、缺口及影响，继续独立可做部分，不假报启用、暂停或完整自动化通过；不另起线程、子代理或外部调度器绕过缺口。
- 可修工程阻塞仅在另行启用熔断复活时按 §2.6.3 处理。其余无依赖阻塞登记滞留，先做独立后续再回收；无法自行解决的线性阻塞立即保存现场并中断受影响链，不挂起等待或轮询。交接记当前状态、事项、证据、已试措施和恢复条件，向用户报告；Goal 状态按宿主机制记录，不伪标完成。
- 已批范围内可即时回写任务状态、实测结论与证据、现场、阻塞及用户明示裁决；规则、需求、范围、权限、例外和未明示版本号仍先拟稿后准入。
- 端口处置默认授权仅限本区治理明写端口且属于本任务的进程，可终止并重启；范围外端口及他人会话不碰。实际终止／重启记入交接，其他端口阻塞按前述分流。

#### 2.6.2 执行：无人值守 - 连续迭代

- 用户直接声明本模式并给出待定项与下个版本号时启用；添加项、轮数／各轮内容和检查间隔按用户指定。给定轮数则按数量与内容止步，未给则完成授权清单即止步。未另定完成条件时，以逐项自审、最终审计、待审副本及交付齐备为终点。
- 先收尾当前已授权版本的未尽并转待审，再按指定版本推进待定项与添加项；未经人工验收保持未落版。每轮只做一项，随即自审、修复、复验，通过后按明确路径开发提交，再取下一项；范围外只登记，遇阻按 §2.6.1。
- 在本模式已批范围内，可按既有骨架整理、写入 HANDOFF 并开发提交任务拆分、待用户审核表、用户明示版本号的接续及事实，无须逐轮再过目；新增治理、需求、范围、权限、例外或未明示版本号仍先拟稿。开发提交不授予落版、常规备份或正式归档。
- 换版前在 T:audit 的本区归属下保存 <版本>-<主题>/ 独立待审副本，说明固定来源、版本增量和查阅入口，可独立查阅且不随施工变化；需运行时该版依赖与构建对应该版并与施工隔离。审计副本与常规版本备份分别记录。
- 现行 HANDOFF 只承载当前施工版本；旧版细节随审计副本留存，当前待用户审核表记版本、真实状态与入口，不预记验收、落版或归档。换版保持一个总 Goal，未尽不清空、不伪标完成；复用本任务 heartbeat 及归属。
- 全部授权事项及最终审计完成后，更新待用户审核表与交接并开发提交，按 §2.6.1 暂停 heartbeat；在会话按指定版本顺序给人工点验入口、步骤、通过条件及缺口。
- 用户确认对应版本后，清理该副本内依赖与构建产物，保留源码、锁文件、审计结论、必要证据及知识交付物；不扩大到其他副本或现场。

#### 2.6.3 执行：熔断复活（可组合策略）

- 用户明确声明本策略并指定范围与完成条件时启用；可与普通执行、无人值守或连续迭代组合，未指定执行方式按普通执行。不增加任务范围、权限或调度能力；未启用不获得复活授权。
- 同一具体阻塞的一轮针对性实施／修正及匹配复验失败计一次，首次即计入；只发现报错、同轮多条错误、重复日志或状态重述不另计。独立问题分账，原问题未解前不因换名、拆分、换会话或报错变化清零。
- 每个阻塞默认失败上限三次，预授权复活两次，每次增加累计上限三次，即 3→6→9；用户明确参数优先。
- 达限先保存必要现场与证据。仍有复活额度，且已有针对失败原因的新修正策略与验证方法时，消耗一次复活继续；否则停受影响链，报告原因、已试措施、证据及恢复条件，继续独立授权事项。全部余项被必要前置阻断时按原执行方式保存并报告，不机械重试；权限、实际额度或外部前置不足不能靠复活解除。
- 解决并通过匹配复验后结束该账，不向其他问题累计；复发时核对是否原阻塞未解，是则沿用原账。
- 在已有交接或证据入口记录阻塞、失败次数、已用复活、当前上限、策略与复验结果。审计、周期检查和宿主阻塞确认轮次另计，不代替实质尝试计数；不自动增加审计轮数，既定验证与验收保持。

### 5.3 核验

核对上述两处共用条款、§2.6 三种模式及其引用全部就位；核对当前核心的预检交互、推理建议时点及普通执行边界仍在，不用旧整份根治理覆盖新核心。

安装不创建 Goal、heartbeat、连续任务或失败账；初始 config 中也不写任务状态。宿主能力检查和实际任务验证分别记录。要验证自动启停，须另行给本任务范围、完成条件和执行授权；尚未实测的能力不记通过。

连续迭代包含开发提交；与无 Git、临时执行或明确禁止提交的任务组合时，先说明冲突，由用户确定可执行口径，不静默创建仓库或删除提交要求。审计副本、常规备份、落版与发布继续分别核对。

## 6. 组合、来源记录与停用

### 6.1 组合与顺序

K／R／M与三个模块分别选用；三个模块之间没有强制安装依赖。知识获取不隐含跨区调度，无人值守不隐含发送或多会话；组合任务只叠加用户已经明确授予的权限。

先核对治理方向、固定材料及现有实现，安放所选原件；合并根治理和规范配套，再统一更新索引、B、保护及必要工具配置。推荐按实际所选K／R／M、知识获取、跨区协作、无人值守的依赖组织改动；可以只选其中一项，不能为凑顺序安装未选项。

三个模块都选时，本区D/spec包含三核心及cache-spec、contract-spec五份规范，由D总INDEX接续登记；K仍按知识需求选择，规范不装入外部共享K。交叉修改合并一次，核心／模块文件、所属索引B、规范目录成员和有效引用分别核实；资料层及继承模式按其原权属保留。

### 6.2 来源与完成

必要文件、配套和约定核验完成后，按根治理 §6 同步 config.modules 的实际来源版本和 D:upstream 的确切模块原件入口，保留其他已采用条目。下例只表示本候选来源形状，不是现在的安装事实，也不是正式发布证明：

  "cross-workspace": {"source_version": "0.1.0.0"},
  "unattended": {"source_version": "0.1.0.0"}

```

只选哪些就记录哪些；未知来源不填核心号代替，K／R／M不加模块条目。单装模块不改变 fieldcase_version；实例版本、K 层版本、消费 pin 和用户验收分别按实际结果维护。

首次采用的模块规则可随获准章程及配套落盘；实际选装工程按本轮任务和三态记录结果、未尽、能力缺口及证据，不写初始化完成标记。返回讨论不把开发中改回待开工，也不自动执行后续业务；仅私有治理维护沿根既有版本／落版边界。

### 6.3 停用与恢复

停用前查现行规则、有效任务、资料引用和本地定制，先拟停用范围与恢复清单；不只删 config 条目。未完成的无人值守任务先按其原授权暂停并核实本任务 heartbeat；未决契约和唯一证据按获准处置保留，不随卸载删除。

规范、模式及配套引用退出后，按批准方案处理当前索引和保护，同步更新该模块的 config 采用记录及 D:upstream 现行入口。保留必要采用原件、迁入来源、用户恢复依据及实际历史。采用方向按根治理 §1.6 办理。仍在使用的知识、材料和契约不能因模块停用失去入口；可选择保留所需模型或先迁移，交用户明确决定。

失败按指南定向修复或恢复；新增、修改、删除、迁移、来源和索引一起核对，不整包覆盖用户实例。范围或权限冲突回讨论，已有事实与未尽如实报告。
